# Changelog

Все заметные изменения в этом проекте будут документироваться в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
и этот проект придерживается [Semantic Versioning](https://semver.org/lang/ru/).

## [Unreleased]

### Added

- Бут-снапшоты базы перед panel-init (M9.3): `backup.BootSnapshot` — отказоустойчивое копирование живого SQLite (перенос в data/, ротация `boot-<ts>.sqlite`, symlink запрещён, атомарные записи); снапшот восстановим без ключей; `test_m93_live.sh` — live E2E потерянной базы.
- Сентинел инициализации `.server-initialized` (M9.3): пишется при `server init`, проверяется до открытия базы — потерянная БД никогда не пересоздаётся пустой схемой, panel-init завершается с инструкцией по восстановлению (restore или копирование бут-снапшота); post-open гвард ловит «схема без серверной записи» (последствие тихого вайпа); self-heal проставляет сентинел для деплоев, инициализированных до M9.3; инжекция отказов (`testFault`) покрывает непровоцируемые публичным API пути ошибок.
- Команда `panel server update [--dns] [--awg-params] [--endpoint]` (M10.1): применяет только переданные флаги на существующую строку сервера (`db.UpdateServer`), `--endpoint ""` явно очищает; awg_params предпроверяется `ParseParams`, endpoint — `validateEndpointArg`; после успешного апдейта `awg0.conf` перегенерируется атомарно (при провале генерации старый конфиг остаётся нетронутым, БД не откатывается — производное состояние).
- Уникальность имён клиентов (M10.1, schema v4): миграция дедуплицирует легаси-дубликаты в `<name>-<id>` (низший id сохраняет чистое имя), затем уникальный индекс защищает вставки и переименования; `ErrClientNameExists` маппится в CLI (exit 1) и в web-слое фиксированным flash-сообщением.
- Хост-стек AmneziaWG в install.sh (M9.2c): ядреный модуль amneziawg + awg-инструменты из официального PPA, авто-загрузка через modules-load.d, DKMS-пересборка после апгрейда ядра; пропуск установки при уже работающем стеке, принудительный режим `AMNEZIA_INSTALL_FORCE_AWG_INSTALL` для тестов.

### Changed

- nftables-правила хоста (M9.2c): forward/input-цепи переведены на priority -100 — accept для подсети VPN оценивается раньше чужих filter-цепей (ufw/docker регистрируются на priority 0 и часто дефолтят FORWARD к DROP).
- forward-accept для сосуществования с docker/ufw (M9.2c): `-i/-o awg0 -j ACCEPT` дополнительно вставляется в начало DOCKER-USER (или FORWARD при его отсутствии), персистится one-shot unit'ом `amnezia-vpn-forward.service` — добавочно, идемпотентно (гвард `iptables -C`), ничего не флашится и не дропается.
- Ошибка `AGE_RECIPIENT is not set` (M10.1) теперь объясняет полную инструкцию (экспорт публичного ключа age в окружение деплоя до `backup create`); подсказка про приватный identity при restore; install.sh в next-steps рекомендует `--dns` для `server init` (полный туннель без DNS-линии сервера теряет локальный DNS) и напоминает про `server update --dns`.
- Live-харнесы: `test_m6_live.sh`/`test_m8_live.sh` — переназначение занятого порта через `M6_PORT` (sed-копия compose с ремапом loopback-маппинга); `test_m5_live.sh` — путь остановки демона в kernel-режиме (удаление интерфейса `ip link del awg0`).
- Тест враждебных имён скачивания бэкапов (M10.1): clean-path-редирект mux'а — 301 с Go 1.22 (а не 307), тест принимает оба кода.
- schema_version БД поднята до 4 (M10.1); бэкапы, снятые до бампа, восстанавливаются только бинарём v3 (манифест версионируется).

### Fixed

- Потерянная или «обнулённая» база под работающим сентинелом больше не пересоздаётся пустой схемой при panel-init — вместо этого воспроизводимые инструкции по восстановлению (M9.3).
- Метрика повторного запуска: тест `test_m5_live.sh` [21] больше не падает, когда userspace-демон отсутствует (kernel-режим) — интерфейс снимается напрямую.

- Репозиторий проекта: техническое задание v2.0, скелет Docker Compose из трёх сервисов (`panel-init`, `panel`, `awg`), Dockerfile и Go-модуль панели, правила .gitignore.
- Зафиксированный инвентарь версий внешних компонентов в `versions.lock` (Go, Alpine, amneziawg-go, amneziawg-tools, modernc.org/sqlite, age, zstd); сборки используют только точные закреплённые коммиты.
- Туннель AmneziaWG в отдельном контейнере: образ из `amneziawg-go` и `amneziawg-tools`, entrypoint ожидает `config/awg0.conf`, поднимает интерфейс через `awg-quick`, следит за его состоянием по UAPI (`awg show`), корректно завершает работу по SIGTERM/SIGINT (`awg-quick down`), при падении туннеля или недоступности конфига завершается с ошибкой.
- SQLite-хранилище: схема из ТЗ (§3: `server`, `clients`, `settings`, `auth`, `schema_meta`), идемпотентные миграции, запись версии схемы в `schema_meta`, команда `panel init`.
- Генератор серверного конфига `awg0.conf` из SQLite: детерминированный рендер, валидация ключей и параметров обфускации AWG (J/S/H/I) по правилам закреплённых версий инструментов, атомарная запись (tmp → fsync → rename → fsync каталога), режим 0600; `panel-init` завершается с ошибкой, если серверная запись отсутствует.
- Горячая перезагрузка конфигурации: AWG-контейнер отслеживает изменение `config/awg0.conf` по mtime и применяет обновления через `awg syncconf` без рестарта туннеля; wg-quick-ключи (`Address`, `DNS`, `MTU`, `ListenPort` и др.) из входных данных syncconf отфильтровываются.
- Генерация ключей X25519 и preshared-ключей средствами стандартной библиотеки Go (`crypto/ecdh`) без новых зависимостей.
- Управление клиентами и сервером в SQLite: bootstrap-запись сервера с новой парой ключей и endpoint'ом в настройках, создание/переименование/включение/отключение/удаление клиентов, срок действия (`expires_at`), атомарное выделение адреса клиента (первый свободный хост в подсети сервера, IPv4) и вставка записи в одной транзакции; просроченные клиенты исключаются из серверного конфига без автоматического удаления.
- Генератор клиентского конфига по запросу: полный IPv4-туннель (`AllowedIPs = 0.0.0.0/0`), endpoint из настроек, зеркалирование серверных параметров обфускации AWG; доступен для клиента независимо от его состояния (`enabled`/`expires_at`).
- Командная строка управления сервером и клиентами в едином бинарё `/app/panel`: `server init` (bootstrap сервера с ключами и endpoint'ом), `client add/list/show/enable/disable/rename/set-expiry/delete/config`; каждая мутация автоматически перегенерирует `awg0.conf`; коды выхода 0 (успех), 1 (операционная ошибка), 2 (неверные аргументы); конфиг выводится только в stdout и не пишется на диск.
- Производитель статуса runtime AWG (M5): producer `awgstatus` в awg-контейнере выполняет `awg show dump` каждый цикл проверки и атомарно пишет `status/status.json` (временный файл → fsync → rename → fsync каталога, режим 0600, схема v1, peers отсортированы по public_key); секретные поля (`private_key`, `preshared_key`) отбрасываются на этапе парсинга и никогда не попадают в файл, память, логи или ошибки; при сбое `awg show` пишется снапшот `has_interface: false` без завершения контейнера; при сбое парсинга предыдущий файл сохраняется.
- Потребитель статуса (M5): команда `panel status` читает `status/status.json` строго на чтение (строгая валидация схемы: неизвестные поля отклоняются), печатает канонический JSON; отсутствие файла → `na` с кодом 0; испорченный файл → код 1 с диагностикой без содержимого файла.
- Веб-панель (M6.1–M6.5): HTTP-сервер `panel serve` — server-side `html/template`, вертикальный стек карточек клиентов (имя, онлайн/офлайн, последний handshake, RX/TX, дата создания; онлайн = handshake ≤ 3 минут), reconciliation SQLite × `status.json` по `public_key` (peer без клиента скрыт, клиент без peer — офлайн, клиент `expires_at` не мутируется), CRUD-операции add/delete/enable/disable/rename/set-expiry через существующий db-слой с атомарной перегенерацией `awg0.conf` под мьютексом, PRG-редиректы (303) с фиксированными flash-сообщениями, generic-страницы ошибок (404/400/413/500 без эха ввода), graceful shutdown по SIGTERM/SIGINT с кодом 0.
- Скачивание клиентского конфига `GET /clients/{id}/config` — байт-в-байт конфиг CLI `client config` (`awgconf.GenerateClient`), `Content-Disposition: attachment` с санитизированным именем файла, работает для disabled/expired клиентов.
- QR-код клиентского конфига `GET /clients/{id}/qr` — PNG 256×256 (запиненный `github.com/skip2/go-qrcode`), payload = тот же конфиг, генерация в памяти без записи на диск.
- Публикация HTTP-порта панели в compose (`127.0.0.1:8787:8787`) — только loopback до аутентификации (M7); шаблоны встраиваются в бинарь через `embed.FS` (Dockerfile не менялся).
- Live E2E-стенд `app/panel/test_m6_live.sh`: полный compose-стек в Docker — panel-init → serve → add по HTTP → download == CLI bytes → QR PNG → awg применяет peer из `awg0.conf` → цикл disable/enable через syncconf → инварианты секретов в HTML/status.json.
- Аудит и контракт M6: `AUDITS/M6_AUDIT.md` — веб-панель (базовый CRUD и карточки клиентов) по ТЗ §6; решения открытых вопросов: Q1 — запиненный QR-энкодер, Q2 — loopback-публикация порта, Q3 — rename/set-expiry в UI; итоговый аудит работ — §12–§13.
- Аутентификация пользователей (M6.2, базис M7): команда `panel auth add-user <username> (--password-stdin | --password-env <ENV>)` — создание первого администратора на свежем VPS без вывода пароля; stdin-пароль читается без эха до EOF (снимаются завершающие `\n`/`\r\n`), env-пароль принимается verbatim; ровно один источник обязателен; дубликат пользователя не перезаписывает существующий.
- Хеширование паролей Argon2id (`internal/auth`, golang.org/x/crypto, запинен `v0.54.0`): параметры по RFC 9106/OWASP reference (`v=19, m=65536,t=1,p=4`, digest 32 Б, соль 16 Б из crypto/rand), PHC-хеш переносит параметры и верифицируется без внешнего состояния, constant-time сравнение, границы длины пароля 1–1024 байт; запиненный cold-вектор в тестах фиксирует диджест.
- Слой доступа к таблице `auth` (`internal/db`): `AuthUserByUsername`, `CreateAuthUser` (с проверкой существования, не перезаписывает), ошибки — фиксированные строки без эха ввода; schema_version не менялась (таблица — часть схемы M2).
- Аудит и контракт M6.2: `AUDITS/M6.2_AUDIT.md` — находки (неограниченное чтение stdin → лимитированное, `x/crypto` в direct, холодный вектор, расхождения commit message), принятые риски, верификация.
- Серверные сессии (M7.3, базис M7): in-memory `SessionStore` — SID из 32 байт `crypto/rand` в base64url (43 символа, cookie-safe), TTL 24 часа absolute без sliding expiration, expired-сессия удаляется лениво при Get, `Delete` идемпотентен, `Rotate` атомарно инвалидирует старый SID (защита от session fixation; после успеха старый SID невалиден навсегда), перезапуск процесса сбрасывает все сессии (ожидаемое поведение); API не знает о `net/http`/cookie/CSRF и не трогает SQLite (schema_version = 3).
- Аудит и контракт M7.3: `AUDITS/M7.3_AUDIT.md` — контракт из задачи, находки (sentinel-конвенция `ErrSessionNotFound`, уточнение логики Get), принятые риски, верификация (`-race -count=3`, регрессы M3.2 58/58 и M5 57/57).
- HTTP-аутентификация панели (M7.4, «панель закрыта по умолчанию»): session-bearer middleware `RequireAuth` (`internal/auth/auth.go`) поверх `SessionStore` M7.3 — каждый маршрут панели (`GET /`, 6 POST-мутаций, `config`, `qr`) обёрнут миддлваром; единственный публичный маршрут — `GET /login` (стаб 501 до формочной реализации M7.5, никогда не редиректит); итоговый 404 для неизвестных путей остаётся публичным.
- Cookie-контракт сессии (M7.4): SID принимается только через заголовок `Cookie: amnezia_session` (никогда в URL/query/form); атрибуты `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure=false` (loopback-HTTP, включается вместе с TLS), lifetime `MaxAge`+`Expires` синхронизирован с TTL хранилища; `WriteSessionCookie`/`ClearSessionCookie` — единственные места работы с cookie, защищённые обработчики токенов не трогают.
- Единая семантика челленджа (M7.4): GET/HEAD без живой сессии → фиксированный `303 /login`; прочие методы (PRG-мутации) → фиксированный `401` + `"Unauthorized.\n"`; ответы никогда не содержат SID, cookie-имени или идентичность; shape-валидация SID (43 байта base64url → 32 байта) до обращения к хранилищу — мусорные cookie не доходят до мьютекса, «форма» и «существование» не различимы снаружи.
- Fail-closed конфигурация (M7.4): `web.New` отклоняет `nil`-session-store (ошибка), `NewAuth(nil)` — panic; `cli serve` создаёт ровно один in-memory store на процесс (рестарт сбрасывает все сессии, контракт M7.3); `internal/auth` не знает о БД/шаблонах/CSRF — готовый фундамент для логина M7.5.
- Тесты безопасности панели (M7.4): автоматрица защиты всех 9 маршрутов (без сессии → 303/401, с сессией → штатный ответ), матрицы unknown/malformed/expired/deleted-сессий, SID-не-утекает (тело, Location, Set-Cookie, Content-Disposition), конкурентность 48/64 параллельных запросов под `-race`, структурная гарантия «в `Session` нет секретных полей» (рефлексия, два пакета), интеграционные cli-проверки на живом сервере (303 → `/login`, отсутствие эха ключевого материала, 404 неизвестных путей с no-follow клиентом).
- Аудит и контракт M7.4: `AUDITS/M7.4_AUDIT.md` — контракт из задачи, находки (паттерн `GET /{$}` против поддерева `GET /`, cli-тесты под публичную панель), принятые риски, верификация (`-race -count=3`, compose-граница).
- Вход в панель (M7.5): `GET /login` — standalone-шаблон (username/password с `autocomplete="username"`/`"current-password"`, без секретов в HTML, авторизованный посетитель → `303 /`); `POST /login` — `AuthUserByUsername` → `VerifyPassword` (Argon2id из M6.2) → сессия → cookie → `303 /` (SID никогда не в URL/query, `next=` не реализован); выход `POST /logout` за `RequireAuth` — удаление сессии, очистка cookie (тот же `Name`/`Path=/`), `303 /login`.
- Единая generic-ошибка логина (M7.5): один фиксированный текст `"Invalid username or password."` для всех режимов (неизвестный пользователь, неверный пароль, пустые credentials, повреждённый PHC-hash) — ответы байт-в-байт идентичны; неизвестный username верифицируется против предвычисленного dummy-хеша Argon2id, чтобы тайминг не выдавал существование аккаунта; повреждённый hash отвечает той же ошибкой, а не 500; DB-ошибка → generic 500 без деталей; провал логина не создаёт сессию и не ставит cookie.
- Сессии при логине (M7.5): валидная cookie → `Rotate` (старый SID навсегда невалиден, защита от session fixation), отсутствующая/протухшая → `Create` с fallback; после каждого успешного входа в store остаётся ровно одна активная сессия пользователя (новый `SessionStore.DeleteByUsername(username, keep)` + снапшот-`ByUsername`, юнит-тесты) — login в новом браузере инвалидирует старые.
- Дашборд (M7.5): «Signed in as {{.Username}}» (username из сессионного контекста, экранируется html/template) + форма logout обычным POST без JS.
- Матрица тестов входа/выхода (M7.5): форма 200/авторизованный-редирект; успешный логин → новый live SID + полный набор cookie-атрибутов; все режимы generic-ошибки; oversize → 413; Create/Rotate/одна-сессия; logout → 303/store-очистка/мертвый старый SID/повторный безличный 401; сканы ответов на password, password_hash, SID, private_key, preshared_key.
- Аудит и контракт M7.5: `AUDITS/M7.5_AUDIT.md` — контракт из задачи, находки (коллизия layout-блоков `title`/`body` у login.html — дашборд рендерился телом логина; ложный позитив SID-скана в Set-Cookie), принятые риски (CSRF → M7.6 зафиксирован в коде и тесте, нет rate-limiting, Secure=false до TLS), верификация (`-race -count=3`, полный M6 web suite, awg 58/58 и 57/57).
- CSRF-защита панели (M7.6): `Session.CSRFToken` — 32 байта из `crypto/rand` (base64url, 43 символа), генерируется при `Create` и `Rotate` (логин ротирует и SID, и CSRF-токен); `RequireCSRF` middleware в `internal/auth` для всех защищённых POST (`/logout`, 6 мутаций дашборда) — токен принимается только из form-поля `_csrf`, constant-time сравнение, GET/HEAD/OPTIONS проходят, `/login` — единственное публичное исключение.
- Интеграция CSRF (M7.6): все 7 форм дашборда несут скрытый `_csrf` (server-side, без JS); невалидный/отсутствующий токен → фиксированный generic 403 `"Forbidden.\n"` без PRG-редиректа и без деталей; токен никогда не попадает в cookie, URL/query, заголовки, логи и flash-сообщения; ротация не выполняется на GET.
- Тест-харднинг M8.8 (покрытие ранее не покрытых состояний): awgstatus-статистика (rx/tx/rate/duration, обнуление счётчиков при рестарте интерфейса); web — error-состояние дашборда, generic 500 при DB-сбое и непрошедшем restore-probe, исчерпание пула адресов (фиксированный flash, ничего не вставлено), generic 500 на внутреннюю ошибку мутации, дефолтная конфигурация сервера; cli — `serve --addr` прокидывает адрес в listener; backup — все не-regular tar-типы (dir/symlink/hardlink/device/fifo) отклоняются с диагностикой без эха содержимого; awgconf — `WriteAtomic` при невозможности rename (цель — каталог) и при недоступном каталоге temps не оставляет частичных файлов и leak'ов; db — `Open` при родителе-файле и родителе без прав записи падает с диагностикой и без файла базы; детерминированный QR-декод (upscale-retry для gozxing R12).

### Changed

- Аудит-документы перенесены в каталог `AUDITS/` (он добавлен в `.gitignore`) — впредь все файлы аудитов хранятся только там и не коммитятся; корневые `M5_AUDIT.md`/`M6_AUDIT.md` выведены из индекса.
- `docs/` добавлен в `.gitignore` и выведен из индекса (как `AUDITS/`): внутренние проектные документы (ТЗ, архитектура, security-заметки) не коммитятся; файлы остаются на диске.
- `auth add-user --password-stdin` читает stdin ограниченно (`LimitReader`, `MaxPasswordLen+2`) — гигантский ввод не буферизуется целиком; валидация длины остаётся за внутренним хешированием.
- go.mod: `golang.org/x/crypto` переведён из indirect в direct (`go mod tidy`); пин зафиксирован в `versions.lock` (`XCRYPTO_GO_VERSION`).
- Веб-фикстура тестов (`internal/web`) теперь несёт валидную администраторскую сессию: `f.get`/`f.serve` ходят авторизованными, тесты «без сессии» строят запрос самостоятельно; `newFixtureWithStore(ttl)` позволяет настраивать TTL для expiry-сценариев.
- Live E2E `test_m6_live.sh` ходит по полному HTTP-стеку (M7.5/M7.6): создание админа через `auth add-user`, логин в cookie jar, извлечение CSRF-токена из дашборда, мутации с `_csrf`, live-проверка «POST без токена → 403», логаут — вместо «сырых» неавторизованных POST-запросов (сломанных закрытием панели в M7.4).
- cli serve-тесты приведены к закрытой панели: `waitForGET` (ожидание 200 на `GET /`) заменён на `waitForServe` (готовность = любой HTTP-ответ), `TestServeHTTPSecretFreeAnd404` проверяет челлендж `303 /login` без эха секретов через no-follow клиент.

### Fixed

- Клиентский конфиг теперь содержит заголовок секции `[Interface]` — без него конфиг не читался бы клиентами AWG.
- Неизвестные GET-пути снова отвечают 404 «из коробки»: паттерн `"GET /"` в `http.ServeMux` — это поддерево (перехватывает все GET, включая несуществующие), поэтому без сессии они уходили в `303 → /login`, а с сессией — во внутренний гвард дашборда; маршрут переведён на точное совпадение `"GET /{$}"`, внутренний гвард удалён — единственный источник 404 теперь публичный catch-all.
- Дашборд снова рендерится своим layout'ом: первый вариант `login.html` определял layout-блоки `title`/`body`, а `ParseFS` парсит шаблоны по алфавиту (последнее определение блока побеждает) — `GET /` стал отдавать тело логин-формы; логин переведён на отдельный standalone-шаблон `"login"` (схема `error.html`), коллизия блоков невозможна по построению.

### Security

- Файл SQLite-базы, содержащий приватные ключи, создаётся и открывается с правами 0600.
- Ошибки операций с ключами никогда не содержат значения приватных и preshared-ключей; приватные ключи не выводятся в списках и журналах.
- Панель не использует Docker socket; `awg` не имеет доступа к SQLite, читает конфигурацию только на чтение, межконтейнерный HTTP отсутствует.
- HTTP-слой панели: таймауты сервера (`ReadHeaderTimeout 5s`, `ReadTimeout 10s`, `WriteTimeout 15s`, `IdleTimeout 60s`, `MaxHeaderBytes 1 MiB`), лимит тела запроса 64 KiB с ответом 413, security-заголовки (`nosniff`, `X-Frame-Options: DENY`, `no-referrer`, CSP `default-src 'self'`, `no-store`), восстановление после panic с generic-страницей 500; инварианты секретов (private/preshared-ключи не попадают в HTML-ответы, ошибки и логи) зафиксированы в `docs/SECURITY.md`.
- Задокументированы security-инварианты и контрмеры в `docs/SECURITY.md` (M6-уровень; порт панели слушает только loopback до аутентификации в M7).
- SID сессии (M7.3) — 256 бит энтропии из `crypto/rand`, не подбирается; сессия несёт только идентификаторы (username, метки времени) и никогда пароли/хеши/ключи — гарантировано структурным тестом.
- Панель закрыта для неавторизованных запросов (M7.4): все маршруты за `RequireAuth`, без живой сессии — `303 /login` (браузер) или `401` (PRG); челленджи и стаб `/login` не раскрывают SID и идентичность; SID-токен не перезаписывается и не попадает ни в один заголовок/тело защищённых ответов; cookie `HttpOnly` + `SameSite=Lax` (защита от XSS-кражи и CSRF-переноса cookie на кросс-сайт POST) — до публикации порта (M7.5+) cookie остаётся `Secure=false`.
- Значения форм никогда не эхоятся в login-ответах (M7.5): провал логина рендерит форму с фиксированным сообщением, username submitted не подставляется обратно в поле; 413-ответ на oversize не содержит ввода.
- Секреты входа (M7.5): пароль существует только как транзиентный аргумент `VerifyPassword`; срок жизни — один Argon2-проход; хеш печатается только в конфиге администратора (M6.2); провалы логина не касаются store; SID нового входа никогда не попадает ни в тело, ни в redirect URL — только в `Set-Cookie` логина.
- Сессии пользователей (M7.5): после успешного входа у пользователя ровно одна активная сессия — «лишние» (другие браузеры/устройства) удаляются; старый SID после Rotate невалиден навсегда.
- CSRF-токен недоступен злоумышленнику (M7.6): хранится только server-side в сессии (поле структурно отделено от каких-либо секретов — структурный тест), передаётся клиенту исключительно скрытым form-полем; форджинг POST-мутаций и `/logout` без токена невозможен даже при подмене SID-cookie (same-site запрос без token → 403); login-форма остаётся CSRF-exempt по контракту M7.5 (SameSite=Lax).
